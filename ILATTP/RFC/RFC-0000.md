# RFC 0000 — ILATTP Core Protocol 1.0

**Document:** RFC 0000

**Title:** ILATTP Core Protocol 1.0

**Status:** Draft

**Version:** 1.0

**Authors:** Arkadiy (blaze_tw)

---

# Abstract

ILATTP (I Love Anna Transfer Protocol) is a lightweight, human-readable application-layer protocol for communication between clients and servers.

The protocol is designed with four primary goals:

- Simplicity
- Readability
- Performance
- Extensibility

ILATTP defines the message format and communication rules but does not define a transport implementation, server architecture, client implementation, or programming language.

---

# 1. Introduction

ILATTP is intended to provide a clean and modern alternative for application-level communication.

The protocol emphasizes:

- easy implementation
- readable messages
- predictable behavior
- future extensibility

The Core specification defines only the minimum required functionality.

Additional features are introduced through Extensions.

---

# 2. Terminology

The keywords **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** are to be interpreted as described in RFC 2119.

---

# 3. Transport

ILATTP is transport independent.

The protocol MAY operate over any reliable byte-stream transport.

Examples:

- TCP
- Unix Domain Socket
- Named Pipe
- Custom Transport

The Core specification does not require any specific transport.

---

# 4. Character Encoding

All textual data MUST use UTF-8 encoding.

Every implementation MUST support UTF-8.

---

# 5. Message Format

Every message consists of:

1. Header
2. Resource (optional)
3. Type (optional)
4. Body (optional)
5. Message Terminator

Example:

```ILATTP 
ILATTP|1.0 FETCH

|user|15

TYPE JSON

{
    "name":"Blaze"
}

<msg-end>
```

---

# 6. Header

The first line MUST follow one of the following formats.

Request:

```text
ILATTP|VERSION METHOD
```

Response:

```text
ILATTP|VERSION STATUS
```

Examples:

```text
ILATTP|1.0 FETCH
```

```text
ILATTP|1.0 SEND
```

```text
ILATTP|1.0 223
```

---

# 7. Methods

Core methods are:

```
HI
BYE
PING

FETCH
SEND
UPDATE
PATCH
REMOVE
```

Method names MUST be uppercase.

---

# 8. Status Codes

Core status codes:

| Code | Meaning |
|------|---------|
|223|Success|
|208|Created|
|118|Bad Request|
|209|Resource Not Found|
|111|Server Error|

Future RFC documents MAY introduce additional status codes.

---

# 9. Resources

Resources identify the target object.

Syntax:

```text
|segment|segment|segment
```

Examples:

```text
|user|15
```

```text
|chat|general
```

Resources are case-sensitive.

---

# 10. TYPE

The TYPE field specifies the body format.

Core formats:

```
JSON
TEXT
BINARY
```

Future extensions MAY introduce additional formats.

Example:

```
TYPE JSON
```

TYPE values MUST be uppercase.

---

# 11. BODY

BODY contains the transmitted payload.

Rules:

- BODY MAY be omitted.
- If BODY exists, TYPE MUST exist.
- If BODY does not exist, TYPE MUST NOT appear.

---

# 12. Message Terminator

Every message MUST end with

```text
<msg-end>
```

A receiver MUST NOT process a message before receiving the terminator.

---

# 13. Line Endings

Implementations MUST accept

- LF (`\n`)
- CRLF (`\r\n`)

Implementations SHOULD generate LF.

---

# 14. Version Compatibility

If the client protocol version is newer than the server version, the server MUST reject the request.

If the server version is newer than the client version, the server MAY accept the request if backward compatibility is supported.

---

# 15. Connection Lifecycle

Typical connection flow:

```
Connect

↓

HI

↓

Request

↓

Response

↓

...

↓

BYE

↓

Disconnect
```

---

# 16. Core Scope

The following features are NOT part of ILATTP Core:

- Authentication
- Ticket System
- Encryption
- Compression
- Streaming
- Routing
- Client implementation
- Server implementation
- ILAON

These features SHALL be defined by separate RFC documents.

---

# 17. Example Request

```ILATTP 
ILATTP|1.0 FETCH

|user|15

<msg-end>
```

---

# 18. Example Response

```text
ILATTP|1.0 223

TYPE JSON

{
    "id":15,
    "name":"Blaze"
}

<msg-end>
```

---

# 19. Compliance

An implementation is considered ILATTP Core 1.0 compliant if it satisfies every mandatory requirement defined in this document.
