# Аннотация

ILATTP (I Love Anna Transfer Protocol) — это лёгкий, человекочитаемый протокол прикладного уровня, предназначенный для обмена данными между клиентами и серверами.

Протокол разработан с четырьмя основными целями:

- Простота
- Читаемость
- Производительность
- Расширяемость

ILATTP определяет формат сообщений и правила взаимодействия, но не определяет конкретную транспортную реализацию, архитектуру сервера, реализацию клиента или язык программирования.

---

# 1. Введение

ILATTP создан как современный и простой протокол обмена данными между приложениями.

Основные принципы протокола:

- простота реализации;
- человекочитаемый формат сообщений;
- предсказуемое поведение;
- возможность расширения без изменения ядра.

Спецификация Core описывает только минимально необходимый функционал.

Все дополнительные возможности определяются отдельными RFC-документами.

---

# 2. Терминология

Ключевые слова **ДОЛЖЕН (MUST)**, **НЕ ДОЛЖЕН (MUST NOT)**, **РЕКОМЕНДУЕТСЯ (SHOULD)**, **НЕ РЕКОМЕНДУЕТСЯ (SHOULD NOT)** и **МОЖЕТ (MAY)** используются в значениях, определённых RFC 2119.

---

# 3. Транспорт

ILATTP не зависит от транспортного уровня.

Протокол может использовать любой надёжный поток байтов.

Например:

- TCP
- Unix Domain Socket
- Именованные каналы (Named Pipe)
- Собственные транспортные реализации

Спецификация Core не требует использования какого-либо конкретного транспорта.

---

# 4. Кодировка

Все текстовые данные ДОЛЖНЫ использовать кодировку UTF-8.

Каждая реализация обязана поддерживать UTF-8.

---

# 5. Формат сообщения

Каждое сообщение состоит из:

1. Заголовка
2. Ресурса (необязательно)
3. Типа данных (необязательно)
4. Тела сообщения (необязательно)
5. Маркера окончания сообщения

Пример:

```text
ILATTP|1.0 FETCH

|user|15

TYPE JSON

{
    "name":"Blaze"
}

<msg-end>
```

---

# 6. Заголовок

Первая строка сообщения должна иметь один из следующих форматов.

Запрос:

```text
ILATTP|VERSION METHOD
```

Ответ:

```text
ILATTP|VERSION STATUS
```

Примеры:

```text
ILATTP|1.0 FETCH
```

```text
ILATTP|1.0 SEND
```

```text
ILATTP|1.0 223
```

---

# 7. Методы

Методы, входящие в Core:

```
HI
BYE
PING

FETCH
SEND
UPDATE
PATCH
REMOVE
```

Названия методов чувствительны к регистру и должны записываться только заглавными буквами.

---

# 8. Коды состояния

Коды состояния Core:

| Код | Значение |
|------|----------|
|223|Успешное выполнение|
|208|Ресурс создан|
|118|Некорректный запрос|
|209|Ресурс не найден|
|111|Ошибка сервера|

Дополнительные коды могут быть определены будущими RFC.

---

# 9. Ресурсы

Ресурсы определяют объект, к которому обращается запрос.

Синтаксис:

```text
|segment|segment|segment
```

Примеры:

```text
|user|15
```

```text
|chat|general
```

Ресурсы чувствительны к регистру.

---

# 10. TYPE

Поле TYPE определяет формат передаваемых данных.

Форматы Core:

```
JSON
TEXT
BINARY
```

Будущие RFC могут определить новые форматы.

Например:

```
TYPE JSON
```

Значения TYPE должны записываться только заглавными буквами.

---

# 11. BODY

BODY содержит передаваемые данные.

Правила:

- BODY может отсутствовать.
- Если BODY присутствует — поле TYPE обязательно.
- Если BODY отсутствует — поле TYPE не должно присутствовать.

---

# 12. Маркер окончания сообщения

Каждое сообщение ILATTP обязательно должно заканчиваться строкой

```text
<msg-end>
```

Получатель не должен начинать обработку сообщения до получения этого маркера.

---

# 13. Перенос строк

Каждая реализация обязана понимать оба варианта переноса строк:

- LF (`\n`)
- CRLF (`\r\n`)

При отправке сообщений рекомендуется использовать LF.

---

# 14. Совместимость версий

Если версия клиента выше версии сервера, сервер обязан отклонить запрос.

Если версия сервера выше версии клиента, сервер может принять запрос при наличии поддержки обратной совместимости.

---

# 15. Жизненный цикл соединения

Типичный порядок работы:

```
Подключение

↓

HI

↓

Запрос

↓

Ответ

↓

...

↓

BYE

↓

Отключение
```

---

# 16. Границы Core

Следующие возможности **не входят** в ILATTP Core:

- Аутентификация
- Система Ticket
- Шифрование
- Сжатие данных
- Потоковая передача
- Маршрутизация (Routing)
- Реализация клиента
- Реализация сервера
- Формат ILAON

Все перечисленные возможности должны определяться отдельными RFC.

---
